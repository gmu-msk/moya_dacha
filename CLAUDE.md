# Как работать в этом репозитории

Правила для агента. Людям — [README.md](README.md) (цикл работы),
[CONTEXT.md](CONTEXT.md) (глоссарий), [docs/adr/README.md](docs/adr/README.md)
(решения и почему). Этот файл не пересказывает их, а говорит, что открывать
и чем это делать.

Язык проекта — русский: спецификации, комментарии, коммиты, имена сценариев.

## Чего не читать

Контекст здесь тратится в основном на чтение лишнего. Порядок величин: весь
репозиторий — около 220 тысяч токенов, из них 49 тысяч (22%) — сгенерированный
код, который читать незачем никогда, и ещё 15 тысяч — `go.sum` и `pubspec.lock`.

| Не открывать | Что вместо |
|---|---|
| `backend/api/gen/**` | типы и сигнатуры видны по `specs/openapi.yaml`; имя метода — `grep` по одной строке |
| `mobile/packages/moya_dacha_api/**` | то же; вызовы клиента — по `mobile/lib/api.dart` |
| `backend/go.sum`, `mobile/pubspec.lock` | версии — в `go.mod` и `pubspec.yaml` |
| `demo/seed/media/*.jpg` | это картинки |
| `specs/openapi.yaml` целиком (7,4 тыс. токенов) | `make api-index` — 36 строк с номерами строк, дальше `sed -n '336,380p'` |
| весь файл ради одной функции | `grep -n` и `sed -n 'N,Mp'` |

Правило поверх таблицы: файл целиком открывается тогда, когда его целиком
собираются менять. Спецификацию фичи, над которой идёт работа, читать целиком
нужно — она источник истины.

Перечитывать файл после собственной правки не надо: правка либо прошла, либо
упала с ошибкой.

## Команды

    make help                     все цели
    make generate                 перегенерировать код из контракта (результат коммитится)
    make test                     гейт: интеграционные тесты (нужен Docker)
    make test-local               тот же гейт без Docker: нативная Postgres на 55432
    make api-index                оглавление контракта вместо чтения openapi.yaml
    make theme-tokens             числа темы для макета: палитры и размеры текста
    make vet build                быстрые проверки Go
    make ci                       всё, что гоняет CI

Гейт один — `backend/tests/`. Приложение проверяется `make app-analyze`
и `make app-test`, это не гейт (ADR-0012).

Макет экрана рисуется из `make theme-tokens`, а не на глаз, и в git не
кладётся: в репозитории живёт ссылка на холст (`specs/000-ui.md`, раздел
«Макеты»). Макет — черновик перед кодом; при расхождении с кодом прав код
(ADR-0018).

## Среда облачной сессии агента

Здесь **нет Docker, Android SDK и `/dev/kvm`**. Значит:

* гейт гонять `make test-local`, а не `make test`;
* `make demo`, `make story`, `make app-apk` здесь не поднимутся — их смотрит
  CI и человек на своей машине, не пытайтесь их чинить локально;
* Flutter ставится (`storage.googleapis.com` открыт), но это ~6 минут:
  ставить только если в PR правда правится Dart, иначе `flutter analyze`
  поймает опечатку в CI.

Артефакты прогона GitHub Actions из этой среды не скачиваются (хранилище
закрыто прокси), лог читается только с хвоста и обрезается по объёму. Поэтому
в CI тесты гоняет `make test-ci`: он печатает полный вывод, а в самом конце —
блок `=== Упало ===` с именами упавших тестов и строками утверждений. При
разборе красного CI читать хвост лога, а не весь лог.

Постоянный список, искать его заново не нужно:

    specs/NNN-slug.md                     спецификация — пишется первой
    specs/000-ui.md                       общие правила интерфейса: правится, только

    specs/openapi.yaml                    контракт: ручки и схемы фичи

`empty_view.dart`, `loading_view.dart` — новых состояний экрана не писать,
брать эти.

## Порядок работы

1. Спецификация и контракт.
2. `make generate` — и не править сгенерированное руками никогда.
3. Тесты пишет **отдельная сессия по спецификации, не видя реализации**
   (ADR-0002). Это же и экономия: реализация не тащит в свой контекст
   рассуждения о тестах.
4. Реализация до зелёного `make test-local`.
5. Сценарий показа в `demo/stories/`.
6. PR черновиком, дальше человек смотрит на телефоне (ADR-0013).

Изменённый тест без изменённой спецификации в том же PR — красный флаг.
Фича без сценария показа — красный флаг.

## Один тред — одна фича

Контекст сессии дорожает от длины, а не от числа сессий. Поэтому:
новую фичу — в новом треде; разбор красного CI, ревью и правку по замечаниям
держать внутри того треда, где живёт PR; не тащить в тред пересказ того,
что уже написано в спецификации или в этом файле.
