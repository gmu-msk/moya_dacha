# Деплой

Прод — один бинарник под systemd, Postgres и Caddy из пакетов (ADR-0004).
Деплой выполняется только из GitHub Actions и только с `main`.

Порядок шага деплоя (ADR-0005):

1. `pg_dump` текущей базы, копия — в объектное хранилище, не на этот VPS
2. `make migrate-up` — миграции, только вперёд
3. замена бинарника и `systemctl restart moya-dacha`

Если миграция упала, старый бинарник продолжает работать на старой схеме,
а на руках свежий дамп.

## Как это устроено

Всё делает workflow `.github/workflows/deploy.yml` на каждый пуш в `main`
(или кнопкой Run workflow). Руками на сервере ничего делать не нужно,
кроме первого шага: дать доступ.

1. Секреты репозитория: `VPS_HOST` (IP), `VPS_USER` (root или пользователь
   с sudo без пароля), `VPS_SSH_KEY` (приватный ключ). Переменная
   репозитория `DOMAIN` — если есть свой домен; без неё адрес сервера
   `<ip-через-дефисы>.sslip.io`, сертификат Caddy получает и на него.
2. `setup.sh` доводит чистую Ubuntu 24.04 до рабочей: подкачка, Postgres 17,
   Caddy, пользователь `moya-dacha`, база с паролем в `/etc/moya-dacha.env`,
   юниты, ночной дамп, файрвол. Если у root есть ключ в
   `authorized_keys`, SSH пускает только по ключу: пароли выключены.
   Повторный запуск ничего не ломает.
3. `release.sh` — сам шаг деплоя по списку ниже.
4. Следом собирается APK с адресом этого сервера и ложится на него же:
   ссылка для тестировщиков — `https://<домен>/app.apk`.

В PR, который трогает деплой, вместо деплоя идёт джоб «Доступ к VPS»:
он только проверяет вход и sudo без пароля, сведений о машине в итоге нет:
репозиторий публичный.

Приглашения на проде — workflow «Приглашение» (Actions → Run workflow):
выдать, отозвать или список. Код приходит владельцу в личку бота, номера
в итоге прогона под маской.

Дашборд владельца — `https://<домен>/dashboard` (specs/016-dashboard.md):
имя любое, пароль `DASHBOARD_PASSWORD` из `/etc/moya-dacha.env`, его
заводит `setup.sh` один раз. Пароль присылает в личку бота workflow
«Дашборд» с действием «пароль», «новый пароль» его ещё и меняет. Тот же workflow раз в два часа проверяет прод
(командой `moya-dacha-server alerts` и запросом к `/api/health` снаружи)
и заводит задачу с меткой «алерт», когда что-то не так.

Ночной дамп — `moya-dacha-backup.timer` в 03:30 UTC, четырнадцать последних
в `/var/backups/moya-dacha`. Он лежит на том же диске, поэтому от потери
самого VPS не спасает; копия наружу — следующий шаг.

## Файлы

- `moya-dacha.service` — юнит systemd, в `/etc/systemd/system/`
- `Caddyfile` — в `/etc/caddy/`, домен подставить свой
- `/etc/moya-dacha.env` — секреты (`DATABASE_URL`, `ADDR`), в git не хранятся

`MEDIA_DIR` — папка с файлами пользователей (аватары, дальше фотографии
постов). Она не в базе и не в git, поэтому в бэкап её нужно класть отдельно
от дампа Postgres (specs/002-profile.md, ADR-0011). Без этой переменной
сервис возьмёт временную папку и скажет об этом в логе — то есть аватары
переживут работу сервиса, но не его перезапуск. `MEDIA_BASE_URL` менять
не нужно: по умолчанию `/media`, и Caddy проксирует его вместе с `/api`.

Пока нет SMS-провайдера, прод работает в режиме приглашений:
`AUTH_INVITES=1` в `/etc/moya-dacha.env` (specs/015-invites.md). Коды
выдаёт тот же бинарник с той же базой:

    sudo -u moya-dacha env $(cat /etc/moya-dacha.env | xargs) moya-dacha-server invite +79001234567
    ... moya-dacha-server invites                  # действующие приглашения
    ... moya-dacha-server uninvite +79001234567    # отозвать

`AUTH_FIXED_CODE` в проде не задаётся никогда: она делает код подтверждения
предсказуемым и существует ради демо-стенда и тестов (specs/001-auth.md).
Если она всё же задана, сервис пишет об этом предупреждение при старте.
