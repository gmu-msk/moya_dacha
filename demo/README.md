# Демо-стенд

Локальный стенд, на котором приложение можно показать: одна команда поднимает
Postgres, накатывает миграции, наливает демо-данные и запускает сервис.

    make demo

Команда сама дождётся ответа от сервиса и напечатает адреса. Нужен только
Docker — Go и Postgres на машине не требуются.

    API                 http://127.0.0.1:8080/api
    Проверка живости    http://127.0.0.1:8080/api/health
    Postgres            postgres://moya_dacha:moya_dacha@127.0.0.1:55433/moya_dacha

Порты слушаются только на `127.0.0.1`: стенд виден с этой машины, а не из
сети. Чтобы до него дошёл телефон, стенд поднимают командой `make demo-lan`
— см. «Приложение на телефоне».

## Команды

| | |
|---|---|
| `make demo` | поднять (или пересобрать и поднять) стенд |
| `make demo-lan` | то же, но видимым в локальной сети — для телефона |
| `make stories` | список сценариев показа user-story |
| `make story STORY=…` | показать один сценарий в эмуляторе |
| `make apk-phone` | собрать APK для телефона с адресом этой машины |
| `make demo-logs` | логи сервиса |
| `make demo-psql` | консоль `psql` в базе стенда |
| `make demo-down` | остановить; данные в базе остаются |
| `make demo-reset` | остановить и стереть базу стенда |

## Что показывать сейчас

Вход по номеру телефона ([specs/001-auth.md](../specs/001-auth.md)) и
профиль — имя, «о себе» и аватар
([specs/002-profile.md](../specs/002-profile.md)):

    make story STORY=001-auth
    make story STORY=002-profile

Код подтверждения на стенде фиксированный — **0000**: SMS-провайдер не
выбран, и стенд поднимается с `AUTH_FIXED_CODE=0000`. В проде переменная
не задаётся, код случайный и уходит в лог сервиса (`make demo-logs`).
Зарегистрированные на стенде номера перечислены в
[stories/001-auth/story.md](stories/001-auth/story.md).

И по-прежнему — что каркас собран целиком: контракт, сгенерированный
роутинг, реализация и настоящая Postgres отвечают по HTTP:

    curl http://127.0.0.1:8080/api/health
    {"status":"ok"}

То же самое показывает приложение строкой состояния внизу экрана.

Дальше эндпоинты появляются на стенде сами: он собирает сервис из текущего
кода, а миграции берёт из `backend/migrations`.

## Показ user-story в эмуляторе

У каждой фичи есть свой сценарий показа: своё имя, свои демо-данные и свой
запуск ([ADR-0009](../docs/adr/0009-demo-story-per-feature.md)). Сценарии
лежат в [stories/](stories/README.md).

    make stories                  # что можно показать
    make story STORY=000-status   # показать

Эмулятор должен быть запущен заранее (`adb devices` показывает устройство).
`make story` стирает базу, поднимает стенд с данными сценария, собирает и
ставит APK, запускает приложение, кладёт снимок экрана в
`demo/out/<сценарий>.png` и печатает список того, что надо проверить глазами.

Для интерактивного показа после этого удобнее `flutter run` из `mobile/`:
стенд уже поднят с нужными данными.

`make demo-e2e` — то же самое без сценария: голая проверка, что путь
эмулятор → приложение → API → Postgres цел.

## Приложение на телефоне

Обычный путь — с одного телефона, без компьютера
([ADR-0013](../docs/adr/0013-testing-from-a-phone.md)).

1. **Поставить сборку.** На каждый пуш в PR CI выкладывает APK черновым
   релизом `pr-<номер>` и пишет в PR один комментарий с прямой ссылкой,
   обновляя его на каждой следующей сборке. Ссылка открывается в браузере
   телефона; Android спросит разрешение ставить приложения из этого
   источника. Репозиторий приватный, поэтому в браузере надо быть
   залогиненным в GitHub.
2. **Поднять стенд.** Комментарий `/стенд` в том же PR поднимает стенд из
   кода этого PR и присылает ответным комментарием публичный адрес:

       /стенд                 на 30 минут, общие демо-данные
       /стенд 002-profile     с данными сценария показа
       /стенд 45              на 45 минут (максимум 60)
       /стенд стоп            погасить сейчас

   Стенд живёт на раннере GitHub Actions, публичный адрес ему даёт быстрый
   туннель Cloudflare. Он гаснет сам, вместе с базой; минуты Actions он
   тратит ровно пока живёт, поэтому потолок — час.
3. **Подключить приложение к стенду.** Внизу любого экрана показан адрес
   сервера; нажатие открывает экран «Сервер». Там «Вставить» (адрес уже
   в буфере, если его скопировали из комментария), «Проверить»,
   «Сохранить». Пересобирать приложение не нужно: адрес не зашит в APK.

Код подтверждения при входе на стенде — **0000**.

Замечания оставляются комментарием в PR.

### Когда компьютер под рукой

Стенд на своей машине и APK с её адресом:

    make demo-lan                 # стенд, видимый в сети
    make apk-phone                # APK с адресом этой машины
    make apk-phone-install        # то же и сразу поставить по USB

`make apk-phone` сам определяет адрес машины в сети, проверяет, что стенд по
нему отвечает, и кладёт APK в `demo/out/`. Если адрес определился неверно
(несколько интерфейсов, VPN), его можно задать руками:

    LAN_IP=192.168.1.10 make apk-phone

Телефон и компьютер должны быть в одной сети Wi-Fi. Адрес, зашитый при
сборке, — значение по умолчанию: если на экране «Сервер» задан другой,
работает он.

Обычный HTTP без TLS Android не разрешает, поэтому `usesCleartextTraffic`
включён — но только в debug-манифесте: в проде перед сервисом стоит Caddy
с сертификатом. У временного стенда адрес и так `https://`.

### `make demo-lan` и безопасность

Обычный `make demo` слушает только `127.0.0.1`: стенд виден с этой машины и
больше ниоткуда. `make demo-lan` открывает порт 8080 на все интерфейсы —
стенд становится виден всем, кто в той же сети. В домашней сети это нормально,
в кафе и коворкинге — нет. Данные на стенде выдуманные, но авторизации у него
нет никакой.

То же и про временный стенд из PR: его адрес публичный, хоть и случайный и
живущий десятки минут. Настоящих персональных данных на стенде быть не
должно — только выдуманные.

## Демо-данные

Общие данные — всё, что лежит в `demo/seed/*.sql`, — применяются к базе после
миграций, по порядку имён файлов (см. [seed/README.md](seed/README.md)).
Поверх них, если стенд поднят под сценарий показа, ложатся данные этого
сценария из `demo/stories/<сценарий>/seed.sql`.

Поднять стенд сразу с данными сценария, не запуская показ целиком:

    DEMO_STORY=000-status make demo

## Как это устроено

`docker-compose.demo.yml` описывает четыре сервиса:

1. `postgres` — Postgres 17, мажорная версия та же, что в тестах и на VPS;
   данные в именованном томе;
2. `migrate` — одноразовый шаг `goose ... up`, отдельно от старта приложения,
   как и в проде ([ADR-0005](../docs/adr/0005-no-staging-forward-only-migrations.md));
3. `seed` — одноразовый шаг, применяющий `demo/seed/*.sql` и, если задан
   `DEMO_STORY`, данные этого сценария показа;
4. `api` — сам сервис, поднимается после обоих шагов.

Образ из `demo/Dockerfile` собирается только для стенда и никуда
не публикуется: в проде контейнеров нет — один бинарник под systemd
([ADR-0004](../docs/adr/0004-binary-and-systemd-in-production.md)).

Стенд не заменяет прод и не является staging-средой: staging в проекте нет
осознанно (ADR-0005). Настоящий сервер описан в [deploy/](../deploy/README.md).
