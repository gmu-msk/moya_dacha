# Спецификация: создание поста

## Статус
Готово

## Зачем (контекст)
Ради этого всё и затевалось: проверяемая гипотеза проекта — станут ли
двадцать дачников регулярно показывать друг другу посадки и урожай
([000-overview](000-overview.md)). Вход ([001-auth](001-auth.md)) и профиль
([002-profile](002-profile.md)) — это подготовка; пост — первое, ради чего
приложение открывают.

Пост — это от одной до десяти фотографий и необязательная подпись.
Поста без медиа не существует: текст сам по себе публикацией не является
([ADR-0006](../docs/adr/0006-post-is-media.md)).

Ленты в этой фиче ещё нет — она следующая ([004-feed](000-overview.md)).
Но пост, который негде увидеть, показать нельзя, поэтому фича заканчивается
экраном самого поста: автор публикует и сразу видит результат.

## Пользовательский сценарий

**Дано:** пользователь вошёл и знаком (у него есть имя).

1. Пользователь нажимает «Новый пост» и выбирает от одной до десяти
   фотографий из галереи. Каждая уходит на сервис сразу, своим запросом.
2. При желании пишет подпись.
3. Публикует. Приложение показывает опубликованный пост: фотографии,
   подпись, автор и когда это было.

**Тогда:** пост существует, у него есть постоянный адрес, и его увидят
все — как только появится лента.

**Если фотографий не выбрано** — кнопка публикации недоступна: поста
без медиа не существует.

## Функциональные требования

1. Пользователь создаёт пост из 1–10 фотографий и необязательной подписи.
   Пост без единой фотографии не создаётся.
2. Фотография загружается отдельным запросом, по одной, и только потом
   становится частью поста. На дачной связи это разница между «одна
   фотография из десяти не долетела, переотправим её» и «начинайте
   всё заново» ([ADR-0014](../docs/adr/0014-media-uploaded-before-the-post.md)).
3. Порядок фотографий в посте задаёт автор — порядком, в котором
   перечислил их при публикации.
4. Подпись — до 1000 символов, можно пустой. Переводы строк разрешены:
   подпись — это текст, а не имя ([002-profile](002-profile.md)).
   Пробельные символы по краям (пробелы и переводы строк в том числе)
   обрезаются, и длина считается уже после обрезки.
5. Фотография — JPEG или PNG не больше 10 МиБ (10 × 1024 × 1024 байт);
   меряется сам файл, а не всё тело запроса. Пикселей — не больше
   8192×8192 по произведению сторон (снимок на 50 Мп проходит);
   это проверяется по заголовку до распаковки, как у аватара
   (002 требование 5). Тип определяется по
   содержимому файла, а не по тому, что сказал клиент.
6. Фотография уменьшается до 1600 по большей стороне (пропорции
   сохраняются, меньшая не увеличивается) и пересохраняется в JPEG.
   Так пост в ленте весит сотни килобайт, а не десятки мегабайт, — при
   дачной связи это разница между «загрузилось» и «приложение не
   работает» ([ADR-0006](../docs/adr/0006-post-is-media.md)).
7. Перед тем как EXIF будет отброшен, фотография разворачивается по
   записанной в нём ориентации: снятое вертикально не должно лечь набок.
   Разворачиваются все восемь вариантов ориентации, зеркальные в том
   числе.
8. Вместе с ключом файла сохраняются ширина и высота фотографии, чтобы
   лента могла занять место под картинку до того, как та загрузится.
   Это размеры уже развёрнутой и уменьшенной фотографии — той, которую
   клиент получит по ссылке.
9. Приложение уменьшает фотографию до тех же 1600 перед отправкой.
   Это про размер запроса, а не про доверие: сервер всё равно нормализует
   то, что пришло.
10. Фотографии лежат в том же хранилище, что и аватары, за тем же
    интерфейсом ([ADR-0011](../docs/adr/0011-files-behind-storage-interface.md)).
11. Загруженная фотография принадлежит тому, кто её загрузил, и может
    попасть только в его пост. Одна фотография — один пост: прикрепить
    её второй раз нельзя.
12. Фотография, загруженная, но так и не опубликованная, не копится
    вечно: публикуя пост, сервис убирает неприкреплённые фотографии
    этого же автора старше часа. Убирает после того, как пост создан,
    и только если он создан: фотография, попавшая в этот самый пост,
    не подметается, сколько бы она до этого ни пролежала, а неудачная
    публикация не убирает ничего. Отдельного расписания в проекте нет
    ([ADR-0004](../docs/adr/0004-binary-and-systemd-in-production.md)),
    и заводить его ради этого не нужно
    ([ADR-0014](../docs/adr/0014-media-uploaded-before-the-post.md)).
13. Пост можно открыть по его адресу. В ответе — автор в публичном
    представлении (идентификатор, имя, аватар) и никогда не номер
    телефона ([CONTEXT.md](../CONTEXT.md)).
14. Открыть пост может любой вошедший пользователь, создать — только
    от своего имени. Чужим именем подписаться нельзя.
15. Фотографии поста после публикации неизменяемы. Подпись автор может
    поправить — это [022-edit-block-delete](022-edit-block-delete.md),
    требование 1 (до него не правилась и подпись).

## Вне рамок (Out of scope)

- **Лента** — следующая фича ([004-feed](000-overview.md)). Здесь пост
  открывается по прямому адресу, на который приложение переходит сразу
  после публикации.
- **Удаление поста** — [007-deletion](000-overview.md). До неё пост,
  опубликованный по ошибке, придётся терпеть; на закрытом тесте это
  переживаемо, а половинчатое удаление без жалоб и без комментариев
  пришлось бы переписывать.
- Лайки ([005](000-overview.md)) и комментарии ([006](000-overview.md)).
- Видео: заложено в модель медиа, но сервер его не принимает
  ([ADR-0006](../docs/adr/0006-post-is-media.md)).
- Редактирование подписи и замена фотографий.
- Обрезка, поворот и фильтры в приложении: берём фотографию как есть.
- Черновики и отложенная публикация.
- Упоминания, теги, ссылки внутри подписи — подпись это просто текст.

## API / контракт данных

Контракт целиком — в [specs/openapi.yaml](openapi.yaml).

### `POST /api/media` — загрузить фотографию

```
Authorization: Bearer <токен>
Content-Type: multipart/form-data, поле `file` — фотография

Response 201: {
  "id": "uuid",
  "kind": "photo",
  "url": "/media/posts/2b7e….jpg",
  "width": 1600,
  "height": 1200
}
Response 400: { "code": "invalid_image",   "message": "..." }
Response 401: { "code": "unauthorized",    "message": "..." }
Response 413: { "code": "image_too_large", "message": "..." }
```

Загруженная фотография ещё не опубликована: она существует, лежит в
хранилище и ждёт, пока автор соберёт из неё пост. Пока пост не создан,
её идентификатор знает только тот, кто её загрузил.

Сам файл, как и аватар, защищён только неугадываемым именем: у кого есть
ссылка, тот и смотрит. Прав на файлы в MVP нет — ни у аватаров, ни
у фотографий постов, и лента всё равно одна на всех
([ADR-0011](../docs/adr/0011-files-behind-storage-interface.md)).

### `POST /api/posts` — опубликовать пост

```
Authorization: Bearer <токен>
Request: {
  "media_ids": ["uuid", "uuid"],
  "caption": "Первая клубника в этом году"
}

Response 201: пост целиком, как у GET /api/posts/{id}
Response 400: { "code": "invalid_request", "message": "..." }
Response 400: { "code": "no_media",        "message": "..." }
Response 400: { "code": "too_many_media",  "message": "..." }
Response 400: { "code": "invalid_media",   "message": "..." }
Response 400: { "code": "invalid_caption", "message": "..." }
Response 401: { "code": "unauthorized",    "message": "..." }
```

Порядок фотографий в посте — порядок идентификаторов в `media_ids`.
Отсутствующий или пустой `media_ids` — это `no_media`, а не
`invalid_request`: запрос понятен, в нём просто нет фотографий.

Проверки идут в этом порядке: сначала число фотографий, потом подпись,
потом сами фотографии. Так на запросе, плохом сразу по двум признакам,
ответ предсказуем.

### `GET /api/posts/{id}` — показать пост

```
Authorization: Bearer <токен>
Response 200: {
  "id": "uuid",
  "created_at": "2026-09-20T10:00:00Z",
  "caption": "Первая клубника в этом году",
  "author": {
    "id": "uuid",
    "name": "Николай",
    "avatar_url": "/media/avatars/6f1c….jpg"
  },
  "media": [
    { "id": "uuid", "kind": "photo", "url": "/media/posts/2b7e….jpg", "width": 1600, "height": 1200 }
  ]
}
Response 401: { "code": "unauthorized", "message": "..." }
Response 404: { "code": "post_not_found", "message": "..." }
```

`author` — публичное представление пользователя: идентификатор, имя,
аватар. Номера телефона в нём нет и быть не может. `kind` у медиа всегда
`photo`: видео заложено в модель, но не принимается.

Ссылки на медиа относительные, как и у аватара, — клиент достраивает их
до адреса сервиса ([ADR-0011](../docs/adr/0011-files-behind-storage-interface.md)).

### Ошибки

| код | статус | когда |
|---|---|---|
| `no_media` | 400 | в `media_ids` нет ни одной фотографии |
| `too_many_media` | 400 | в `media_ids` больше десяти фотографий |
| `invalid_media` | 400 | фотографии нет, она чужая или уже в другом посте |
| `invalid_caption` | 400 | подпись длиннее 1000 символов |
| `invalid_image` | 400 | файл не JPEG и не PNG или не читается как картинка |
| `invalid_request` | 400 | тело запроса не разбирается; в загрузке нет поля `file` |
| `image_too_large` | 413 | фотография больше 10 МиБ или больше 8192×8192 точек |
| `unauthorized` | 401 | нет токена или он недействителен |
| `post_not_found` | 404 | поста с таким идентификатором нет |

## Модель данных

```
posts
  id          uuid primary key
  author_id   uuid not null references users(id)
  caption     text not null default ''
  created_at  timestamptz not null default now()

media
  id          uuid primary key
  author_id   uuid not null references users(id)
  post_id     uuid references posts(id) on delete cascade  -- NULL, пока не опубликовано
  position    int                                          -- 1..10, порядок автора
  kind        text not null            -- 'photo'; задел под видео
  storage_key text not null            -- posts/<случайное имя>.jpg
  width       int  not null
  height      int  not null
  created_at  timestamptz not null default now()
  unique (post_id, position)
```

Медиа — отдельная таблица, а не массив ключей в посте: у медиа есть
собственные поля (размеры, вид), оно живёт до поста, а видео, когда до
него дойдёт, добавит свои. `on delete cascade` — чтобы удаление поста
([007-deletion](000-overview.md)) не оставляло висящих строк.

`post_id IS NULL` означает «загружено, но не опубликовано». Прикрепление —
это перевод строки из этого состояния в опубликованное, и он одноразовый:
именно поэтому одну фотографию нельзя положить в два поста.

Как и у аватара, в базе лежит **ключ** файла, а не ссылка: ссылку сервис
строит из ключа сам.

## Ограничения и edge cases

| ситуация | поведение |
|---|---|
| Одна фотография, без подписи | пост создаётся |
| Четыре фотографии | пост создаётся, порядок сохраняется |
| Одиннадцать фотографий | `400 too_many_media` |
| Пустой `media_ids` | `400 no_media` |
| Только подпись, без фотографий | `400 no_media` |
| Один и тот же идентификатор дважды | `400 invalid_media` |
| Чужая фотография в `media_ids` | `400 invalid_media` |
| Фотография, уже опубликованная в другом посте | `400 invalid_media` |
| Несуществующий идентификатор фотографии | `400 invalid_media` |
| Идентификатор фотографии не похож на UUID | `400 invalid_media` |
| Хотя бы один идентификатор плохой | пост не создаётся целиком |
| Подпись из пробелов | сохраняется пустой: пробелы по краям обрезаются |
| Подпись в 1000 символов | сохраняется: считаются символы, а не байты |
| Подпись длиннее 1000 символов | `400 invalid_caption` |
| Перевод строки в подписи | сохраняется как есть |
| Фотография — PNG | принимается, сохраняется как JPEG |
| Текстовый файл с именем `photo.jpg` | `400 invalid_image` |
| GIF или WebP | `400 invalid_image`: в MVP только JPEG и PNG |
| Фотография больше 10 МиБ | `413 image_too_large` |
| PNG в 100 КБ, объявляющий 30000×30000 | `413 image_too_large` |
| Фотография меньше 1600 по большей стороне | сохраняется как есть, не увеличивается |
| Фотография снята вертикально (EXIF orientation) | разворачивается, не ложится набок |
| Загрузка без поля `file` | `400 invalid_request` |
| Загруженная и не опубликованная фотография | через час убирается при следующей публикации этого автора |
| Неопубликованная фотография моложе часа | остаётся: автор ещё собирает пост |
| Любой из запросов без токена | `401 unauthorized` |
| Идентификатор поста не похож на UUID | `404 post_not_found` |
| Чужой или несуществующий идентификатор поста | `404 post_not_found` |
| Пост другого пользователя | открывается: лента одна на всех |

Пост создаётся целиком или не создаётся вовсе: если хотя бы одна
фотография не прикрепилась, в базе не появляется ни поста, ни изменений
в медиа.
