# Спецификация: <название фичи>

## Статус
Черновик / В работе / Готово

## Зачем (контекст)
Кратко: какую проблему пользователя решает эта фича, почему она нужна в MVP.

## Пользовательский сценарий
Как пользователь взаимодействует с фичей, шаг за шагом (можно в формате
"Дано / Когда / Тогда").

## Функциональные требования
Явный список того, что должно работать. Нумеровать, чтобы легко ссылаться.

1. ...
2. ...

Требование к виду, одинаковое на всех экранах (прокрутка, ожидание, пустое
состояние, подтверждение), сюда не пишется: для него есть
[общие правила интерфейса](000-ui.md).

## Вне рамок (Out of scope)
Что сознательно НЕ делаем в этой версии — чтобы вайбкодинг не "доизобретал"
лишнего.

## API / контракт данных
Эндпоинты, поля, форматы запросов/ответов, коды ошибок. Для фронта и бэка —
единый источник истины.

```
Пример:
POST /api/posts
Request: { "text": string, "image_url": string }
Response 201: { "id": string, "created_at": string, ... }
Response 400: { "error": string }
```

## Модель данных
Таблицы/поля, связи, ограничения (уникальность, обязательность и т.д.).

## Ограничения и edge cases
Что должно происходить в нестандартных ситуациях (пустой ввод, дубликаты,
превышение лимитов, отсутствие сети и т.д.).

Отдельно — что человек видит, когда показывать нечего или что-то пошло не
так: текст пустого состояния и тексты ошибок. Их пишет спецификация, а не
код ([ADR-0012](../docs/adr/0012-theme-and-shared-widgets.md)).
