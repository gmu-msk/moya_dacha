# Спецификация: регистрация и вход по номеру телефона

## Статус
Готово

## Зачем (контекст)
В МояДаче всё привязано к пользователю: пост, лайк и комментарий имеют автора,
а жалоба — отправителя. Поэтому вход — первая фича MVP: без неё ни одна
следующая не имеет смысла.

Пользователь опознаётся номером телефона ([CONTEXT.md](../CONTEXT.md)):
паролей в продукте нет, вход — одноразовый код на номер. Для закрытой группы
дачников это самый короткий путь внутрь: телефон помнят все, пароль забывают.

Регистрация и вход — одно и то же действие. Пользователь вводит номер и код;
если такого номера ещё нет, он появляется. Отдельного экрана регистрации нет
и не будет: два пути с одинаковыми полями — лишний выбор на пустом месте.

## Пользовательский сценарий

**Дано:** приложение установлено, пользователь его открыл и ещё не входил.

1. Пользователь видит экран входа, вводит номер своего телефона и нажимает
   «Получить код».
2. Сервис принимает номер, выдаёт код подтверждения и отправляет его на этот
   номер. Пока SMS-провайдер не подключён, «отправка» — это запись кода
   в лог сервиса, откуда владелец сервиса выдаёт код тестировщику вручную
   (см. [specs/000-overview.md](000-overview.md), «Внешние зависимости»).
3. Пользователь вводит код и нажимает «Войти».
4. Сервис проверяет код. Если номера ещё нет — заводит пользователя.
   В ответ приходит токен сессии.
5. Приложение сохраняет токен и показывает, что вход выполнен.

**Тогда:** при следующем запуске приложение открывается уже внутри — токен
лежит в памяти устройства и не истекает, пока пользователь не вышел сам.

**Если код не тот** — приложение говорит об этом и оставляет пользователя
на том же экране: у него есть ещё попытки и возможность запросить код заново.

## Функциональные требования

1. Пользователь запрашивает код подтверждения на номер телефона.
2. Номер нормализуется: `+7 (900) 123-45-67`, `8 900 123 45 67` и
   `79001234567` — один и тот же пользователь. Хранится и сравнивается
   нормализованный вид `+79001234567`.
3. В MVP принимаются только российские мобильные номера: ровно 11 цифр,
   первая — `7` или `8`, вторая — `9`, то есть `+79XXXXXXXXX`. Всё
   остальное — ошибка `invalid_phone`. Не-цифры (пробелы, скобки, дефисы,
   ведущий `+`) при разборе отбрасываются.
4. Код — четыре цифры. Живёт 5 минут с момента выдачи.
5. Повторный запрос кода на тот же номер разрешён не чаще одного раза
   в 60 секунд; более частый запрос — ошибка `too_many_requests`.
6. Новый запрос кода на тот же номер отменяет предыдущий код: действует
   всегда только последний.
7. На один код — не более 5 попыток ввода. Исчерпанные попытки сжигают код:
   дальше нужен новый.
8. Верный код в пределах срока жизни создаёт сессию и возвращает токен.
   Использованный код сгорает: второй раз тем же кодом войти нельзя.
9. Если номера в базе нет, пользователь создаётся в этот момент. Ответ
   помечает такой вход как первый (`is_new_user`), чтобы приложение могло
   потом отвести нового пользователя заполнять профиль (см. 002-profile).
10. Токен сессии передаётся в заголовке `Authorization: Bearer <токен>`
    и не истекает по времени.
11. Пользователь может посмотреть свою сессию: кто он и когда
    зарегистрировался.
12. Пользователь может выйти — токен перестаёт действовать. Остальные
    его сессии (другое устройство) продолжают работать.
13. Отправка кода спрятана за интерфейсом: подключение SMS-провайдера
    не меняет контракт и не трогает хендлеры.
14. Для стенда и тестов есть режим фиксированного кода: переменная
    окружения `AUTH_FIXED_CODE` задаёт код, который сервис выдаёт всегда.
    В проде она пуста, и код случайный.
15. Сроки из пунктов 4 и 5 — настройки сервиса со значениями по умолчанию
    из этой спеки (5 минут и 60 секунд). Тесты поднимают сервис с короткими
    сроками: иначе проверка «код истёк» стоила бы пять минут прогона.
    Ответ `POST /api/auth/code` всегда сообщает те сроки, с которыми сервис
    работает на самом деле.

## Вне рамок (Out of scope)

- Настоящая отправка SMS: провайдер не выбран (вопрос владельца сервиса).
- Вход по паролю, по почте, через сторонние сервисы.
- Срок жизни токена, продление, refresh-токены. Токен живёт, пока
  пользователь не вышел.
- Список своих устройств и выход «везде».
- Смена номера телефона.
- Удаление аккаунта и блокировка пользователя — оба потребуются перед
  публичным релизом ([000-overview.md](000-overview.md)), но не в MVP.
- Защита от перебора номеров с одного устройства (капча, лимит по IP):
  на закрытой группе в 20 человек это преждевременно.
- Имя и аватар пользователя — это 002-profile.

## API / контракт данных

Контракт целиком — в [specs/openapi.yaml](openapi.yaml). Здесь — то же
самое словами.

### `POST /api/auth/code` — запросить код

```
Request:  { "phone": "+7 900 123-45-67" }
Response 202: { "resend_after": 60, "code_ttl": 300 }
Response 400: { "code": "invalid_phone", "message": "..." }
Response 429: { "code": "too_many_requests", "message": "..." }
```

Ответ одинаков и для существующего номера, и для нового: по нему нельзя
узнать, зарегистрирован ли человек. `resend_after` — через сколько секунд
можно запросить код снова, `code_ttl` — сколько живёт выданный код.

### `POST /api/auth/session` — войти по коду

```
Request:  { "phone": "+7 900 123-45-67", "code": "1234" }
Response 200: {
  "token": "…",
  "is_new_user": true,
  "user": { "id": "uuid", "phone": "+79001234567", "created_at": "2026-09-20T10:00:00Z" }
}
Response 400: { "code": "invalid_phone", "message": "..." }
Response 401: { "code": "invalid_code",     "message": "..." }
Response 401: { "code": "code_expired",     "message": "..." }
Response 401: { "code": "too_many_attempts","message": "..." }
```

`invalid_code` отвечается и на неверный код, и на код, которого никто
не запрашивал: подтверждать, что по номеру есть живой код, незачем.

### `GET /api/auth/session` — кто я

```
Authorization: Bearer <токен>
Response 200: { "user": { "id": "uuid", "phone": "+79001234567", "created_at": "..." } }
Response 401: { "code": "unauthorized", "message": "..." }
```

### `DELETE /api/auth/session` — выйти

```
Authorization: Bearer <токен>
Response 204: пусто
Response 401: { "code": "unauthorized", "message": "..." }
```

Выход идемпотентен по смыслу «этого токена больше нет»: повторный вызов
с тем же токеном отвечает `401`, потому что токен уже недействителен.

### Ошибки

| код | статус | когда |
|---|---|---|
| `invalid_phone` | 400 | номер не разбирается или не российский мобильный |
| `invalid_request` | 400 | тело запроса не разбирается или поле пустое |
| `too_many_requests` | 429 | код на этот номер запрашивали меньше минуты назад |
| `invalid_code` | 401 | код не тот или не запрашивался |
| `code_expired` | 401 | код выдан больше 5 минут назад |
| `too_many_attempts` | 401 | по этому коду исчерпаны 5 попыток |
| `unauthorized` | 401 | нет заголовка `Authorization` или токен недействителен |

## Модель данных

```
users
  id          uuid        PK
  phone       text        NOT NULL, UNIQUE   -- нормализованный, +79XXXXXXXXX
  created_at  timestamptz NOT NULL

auth_codes                                   -- не более одного живого кода на номер
  phone         text        PK
  code_hash     text        NOT NULL         -- sha256, в открытом виде код не хранится
  attempts_left int         NOT NULL
  expires_at    timestamptz NOT NULL
  created_at    timestamptz NOT NULL

sessions
  token_hash  text        PK                 -- sha256 токена; сам токен есть только у клиента
  user_id     uuid        NOT NULL -> users(id) ON DELETE CASCADE
  created_at  timestamptz NOT NULL
```

Ни код, ни токен не хранятся в открытом виде: в базе лежат их sha256.
Для токена это защита: 32 случайных байта из хеша не восстановить, и утечка
дампа не даёт войти ни под кем. Для кода это не защита от перебора — четыре
цифры перебираются мгновенно, — а способ не показать живой код тому, кто
читает дамп; живёт такой код всё равно пять минут.

Строка в `auth_codes` живёт на номер, а не на пользователя: код запрашивают
и те, кого в `users` ещё нет.

## Ограничения и edge cases

| ситуация | поведение |
|---|---|
| Номер с пробелами, скобками, дефисами | нормализуется, это тот же номер |
| Номер, начинающийся с `8` | тот же номер, что и с `+7` |
| Номер не российский или не мобильный | `400 invalid_phone` |
| Пустой номер или пустой код | `400 invalid_request` |
| Код запрошен дважды подряд | второй раз в течение минуты — `429`, первый код остаётся живым |
| Код запрошен после минуты | выдаётся новый; старый больше не подходит |
| Код введён после 5 минут | `401 code_expired` |
| Шестая попытка по одному коду | `401 too_many_attempts`, дальше только новый код |
| Правильный код введён дважды | второй раз — `401 invalid_code`: код сгорел при входе |
| Вход с двух устройств | две сессии, два токена, оба работают |
| Выход на одном устройстве | второе устройство продолжает работать |
| `Authorization` без `Bearer` или с чужим токеном | `401 unauthorized` |
| Номер телефона в публичном представлении автора | не бывает: телефон возвращается только владельцу сессии |

Проверки кода идут в одном порядке: сначала срок жизни (`code_expired`),
потом исчерпанные попытки (`too_many_attempts`), потом совпадение
(`invalid_code`). Так у ответа всегда одна причина, даже когда верны
несколько.
