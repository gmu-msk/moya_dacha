# Спецификация: вход по коду приглашения

## Статус
В работе

## Зачем (контекст)
Закрытый тест идёт на настоящем сервере с настоящими людьми, а SMS-провайдера
нет и до конца MVP не будет: SMS дорогие. Сейчас без него есть два способа
войти, и оба не годятся. Код из лога сервиса владелец должен передавать
каждому тестировщику руками в течение пяти минут. Общий код стенда
(`AUTH_FIXED_CODE`) пускает любого под любым номером.

Поэтому на время теста вход идёт по **коду приглашения**. Владелец сервиса
выдаёт человеку личный код, привязанный к его номеру, и пересылает его сам
удобным способом. Человек вводит номер и этот код на том же экране входа,
что и раньше. Без приглашения войти нельзя, под чужим номером тоже:
код подходит только к своему номеру.

Это режим сервиса, а не замена 001-auth. Когда появится SMS-провайдер,
режим выключается, и вход снова идёт по коду из SMS.

## Пользовательский сценарий

**Дано:** сервис работает в режиме приглашений. Владелец выдал приглашение
на номер `+7 900 123-45-67` и переслал дачнику код `4821`.

1. Дачник открывает приложение, вводит свой номер и нажимает «Получить код».
2. Сервис видит приглашение на этот номер и отвечает, что код приглашения
   у человека уже есть. Ничего никуда не отправляется.
3. Приложение открывает экран кода с подсказкой «Введите код из приглашения».
   Кнопки «Отправить ещё раз» и счётчика на этом экране нет: новый код
   может выдать только владелец.
4. Дачник вводит `4821`, и вход уходит сам после четвёртой цифры, как
   при обычном коде.
5. Сервис проверяет код, заводит пользователя, если его ещё нет, и
   выдаёт сессию. Приглашение на этом сгорает.

**Тогда:** дачник внутри приложения, дальше всё как после обычного входа
(001-auth), новый пользователь идёт знакомиться (002-profile, 010-nicknames).

**Если номера нет в приглашениях** — приложение остаётся на экране номера
и говорит под полем, что для входа нужен код приглашения от владельца.

**Если дачник вышел или сменил телефон** — владелец выдаёт ему новое
приглашение на тот же номер. Аккаунт, посты и подписки остаются прежними:
пользователь опознаётся номером.

## Функциональные требования

1. Режим включается переменной окружения `AUTH_INVITES=1` (любое непустое
   значение). Без неё сервис работает ровно как в 001-auth.
2. В режиме приглашений сервис не выдаёт и не отправляет кодов
   подтверждения. `AUTH_FIXED_CODE` в этом режиме не действует.
3. Приглашение — пара «номер + код». Код — четыре случайные цифры, как код
   подтверждения, чтобы экран входа оставался тем же. В базе хранится
   sha256 кода, сам код знает только тот, кто приглашение выдал.
4. На один номер действует не больше одного приглашения. Новое приглашение
   на тот же номер заменяет прежнее: старый код больше не подходит,
   попытки начинаются заново.
5. Срока жизни у приглашения нет: оно действует, пока им не вошли, пока
   его не отозвали или пока не кончились попытки.
6. На одно приглашение — не более 5 попыток ввода, как у кода
   подтверждения. Исчерпанные попытки сжигают приглашение: дальше нужно
   новое.
7. `POST /api/auth/code` в режиме приглашений:
   - номер нормализуется и проверяется так же, как в 001-auth;
   - если на номер есть приглашение с оставшимися попытками, ответ `202`
     с `delivery: "invite"`, а `resend_after` и `code_ttl` равны нулю;
   - если приглашения нет или попытки по нему кончились, ответ
     `403 not_invited`;
   - ограничение «не чаще раза в минуту» не действует: запрос ничего
     не отправляет.
8. Вне режима приглашений `POST /api/auth/code` отвечает как раньше
   и добавляет `delivery: "sent"`.
9. `POST /api/auth/session` в режиме приглашений проверяет код по
   приглашению на этот номер. Порядок проверок: сначала исчерпанные
   попытки (`too_many_attempts`), потом совпадение (`invalid_code`).
   `code_expired` в этом режиме не бывает.
10. Верный код создаёт сессию так же, как в 001-auth (новый пользователь
    заводится здесь же, `is_new_user`), и сжигает приглашение.
11. Приглашения выдаёт владелец сервиса командами того же бинарника,
    на сервере, с той же `DATABASE_URL`:
    - `moya-dacha-server invite <номер>` выдаёт приглашение и печатает
      нормализованный номер и код;
    - `moya-dacha-server uninvite <номер>` отзывает приглашение;
    - `moya-dacha-server invites` печатает все действующие приглашения:
      номер, когда выдано, сколько попыток осталось. Кодов в этом списке
      нет, они не хранятся.
    Неверный номер — ошибка с понятным текстом и ненулевой код выхода.
    Вывод для публичного лога — требование 18.
12. Приглашение выдаётся и на номер, который уже зарегистрирован: так
    человек входит заново после выхода или с нового телефона.
13. Приложение по `delivery: "invite"` показывает на экране кода подсказку
    «Введите код из приглашения» и не показывает ни счётчика, ни кнопки
    повторной отправки. Кнопка «Другой номер» остаётся.
14. Ответ `403 not_invited` приложение показывает как ошибку под полем
    номера, текстом из ответа сервиса.
15. Вход по приглашению не требует предварительного запроса кода:
    `POST /api/auth/code` ничего не выдаёт, и вход проверяет только
    приглашение.
16. Вне режима приглашений выданные приглашения ничего не значат: код
    приглашения не впускает, запрос кода подчиняется лимиту 001-auth.
17. Приглашение с исчерпанными попытками остаётся в таблице с нулём
    попыток, но действующим не считается: в `invites` его нет, запрос
    кода отвечает `not_invited`.
18. Команды запускаются и из прогона GitHub Actions, а репозиторий
    публичный: всё, что команда печатает, видно всем. Поэтому с переменной
    окружения `PUBLIC_OUTPUT=1` (любое непустое значение):
    - `invite` не печатает код, а отправляет его владельцу в личку
      Telegram-бота ([018](018-telegram-bot.md)) вместе с полным номером;
      печатается только номер под маской и то, что код ушёл в Telegram;
    - если бот не настроен или личка владельца не привязана, `invite`
      завершается ошибкой, и приглашение **не выдаётся**: код, который
      никто не увидит, бесполезен, а напечатать его нельзя;
    - `uninvite` и `invites` печатают номера под маской: видны код страны
      и последние четыре цифры, `+7 *** ***-45-67`.
    Та же переменная прячет лишнее и в выводе `telegram-check`
    ([018](018-telegram-bot.md), требование 3а).
    Без переменной команды печатают всё как раньше: так ими пользуются
    на сервере по SSH.

## Вне рамок (Out of scope)

- Выдача приглашений из приложения, с дашборда или по ссылке. Пока только
  командой на сервере; удобная кнопка для владельца придёт позже.
- Приглашения, которые пользователи выдают друг другу.
- Срок жизни приглашения и его автоматическая чистка.
- Отзыв уже выданных сессий при отзыве приглашения: отзыв касается только
  ещё не использованного кода.
- Настоящая отправка SMS (001-auth, «Вне рамок»).

## API / контракт данных

Контракт целиком — в [specs/openapi.yaml](openapi.yaml). Меняется одна
схема и добавляется один ответ.

### `POST /api/auth/code`

```
Request:  { "phone": "+7 900 123-45-67" }
Response 202 (обычный режим):      { "delivery": "sent",   "resend_after": 60, "code_ttl": 300 }
Response 202 (режим приглашений):  { "delivery": "invite", "resend_after": 0,  "code_ttl": 0 }
Response 400: { "code": "invalid_phone", "message": "..." }
Response 403: { "code": "not_invited",   "message": "..." }   -- только в режиме приглашений
Response 429: { "code": "too_many_requests", ... }             -- только в обычном режиме
```

`delivery` — обязательное поле: как человек получит код. `sent` — сервис
отправил код на номер, `invite` — код у человека уже есть в приглашении.

### `POST /api/auth/session`

Запрос и ответы те же, что в 001-auth. В режиме приглашений `code_expired`
не отвечается.

### Ошибки

| код | статус | когда |
|---|---|---|
| `not_invited` | 403 | режим приглашений, а на номер нет действующего приглашения |
| `invalid_code` | 401 | код не совпал с приглашением или приглашения нет |
| `too_many_attempts` | 401 | по приглашению исчерпаны 5 попыток |

Остальные ошибки — как в 001-auth.

## Модель данных

```
invites                                    -- не более одного приглашения на номер
  phone         text        PK             -- нормализованный, +79XXXXXXXXX
  code_hash     text        NOT NULL       -- sha256 кода
  attempts_left int         NOT NULL
  created_at    timestamptz NOT NULL
```

Таблица живёт на номер, а не на пользователя: приглашают и тех, кого
в `users` ещё нет. `auth_codes` в режиме приглашений не используется.

## Ограничения и edge cases

| ситуация | поведение |
|---|---|
| Режим выключен | всё как в 001-auth, в ответе на запрос кода `delivery: "sent"` |
| Режим включён, номера нет в приглашениях | запрос кода — `403 not_invited`; вход — `401 invalid_code` |
| Режим включён, приглашение есть | запрос кода — `202 delivery: "invite"`, нули в сроках |
| Номер в приглашении и в запросе записан по-разному (`8 900…` и `+7 900…`) | это один номер |
| Запрос кода по приглашению дважды подряд | оба раза `202`, `429` не бывает |
| Верный код приглашения | вход, приглашение сгорает |
| Тот же код второй раз | `401 invalid_code` |
| Неверный код 5 раз, затем верный | шестая попытка — `401 too_many_attempts`; запрос кода после этого — `403 not_invited` |
| Приглашение выдано заново | старый код — `401 invalid_code`, новый подходит, попытки снова 5 |
| Приглашение отозвано | запрос кода — `403 not_invited`, вход — `401 invalid_code` |
| Приглашение на уже зарегистрированный номер | вход в тот же аккаунт, `is_new_user: false` |
| Режим включён и задан `AUTH_FIXED_CODE` | фиксированный код не подходит, действуют только приглашения |
