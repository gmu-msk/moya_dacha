# Спецификация: отчёты об ошибках приложения

## Статус
В работе

## Зачем (контекст)
Тестировщики не пишут «у меня всё зависло»: они закрывают приложение и
идут дальше. На маленькой группе ошибка, которую видели двое, — это
половина багов, и узнать о ней можно только из самого приложения.

Приложение ловит свои необработанные ошибки и отправляет их на сервер.
Сервер склеивает повторы одной и той же ошибки, показывает их на
дашборде рядом с ошибками сервера, а о каждой новой ошибке бот сразу
пишет владельцу в личку.

Задача: [#48](https://github.com/gmu-msk/moya_dacha/issues/48), этап 2.
Дашборд — [016-dashboard](016-dashboard.md), бот —
[018-telegram-bot](018-telegram-bot.md). Почему своё, а не Crashlytics
или Sentry, — [ADR-0024](../docs/adr/0024-app-errors-inside-the-service.md).

## Пользовательский сценарий

**Дано:** тестировщица вошла в приложение, личка владельца привязана
к боту, владелец может открыть дашборд.

1. Тестировщица открывает пост, и на экране что-то ломается: вместо
   поста серый экран или приложение перестаёт отвечать на касание.
2. Приложение молча отправляет отчёт: текст ошибки, стек, версию и
   сборку, экран, телефон. Тестировщица ничего не видит.
3. Через минуту владельцу в личку приходит «Новая ошибка в приложении»
   с текстом ошибки, местом в коде, сборкой, экраном и ником
   тестировщицы.
4. Та же ошибка случается у соседа. Бот молчит: ошибка не новая.
5. Владелец открывает дашборд. В разделе «Ошибки приложения» — эта
   ошибка: 2 отчёта от 2 человек, когда была первый и последний раз,
   в какой сборке и на каком экране; стек раскрывается по касанию.

## Функциональные требования

### Отчёт
1. Отчёт — `POST /api/app-errors` с телом:
   - `error` — текст ошибки, обязателен, от 1 до 2000 символов;
   - `stack` — стек, до 20000 символов, можно не прислать;
   - `version` — версия приложения, до 32 символов, можно не прислать;
   - `build` — номер сборки, целое от 0, можно не прислать (это 0);
   - `screen` — экран, на котором был человек, имя по таблице
     specs/020-app-sessions.md (требование 10): от 1 до 32 символов
     `a-z` и `_`; можно не прислать;
   - `os` — система телефона, до 100 символов, можно не прислать.

   Ответ — `204`. Поле не по правилам — `400 invalid_report`, отчёт
   не записывается.
2. Время отчёта ставит сервер по своим часам.
3. Токен не обязателен: ошибка может случиться и до входа (экраны входа
   и «Сервер»). С действительным токеном отчёт записывается от имени
   человека, без токена или с недействительным — как отчёт без входа.
   `401` эта ручка не отвечает.
4. Отчётов от одного человека принимается не больше 100 за последний час,
   отчётов без входа — не больше 100 за последний час на всех вместе.
   Сверх этого — `429 too_many_reports`, отчёт не записывается.

### Одна и та же ошибка
5. Отчёты одной ошибки склеиваются в группу. Два отчёта — одна ошибка,
   если у них совпадают текст ошибки и первые 5 непустых строк стека.
   При сравнении цифры не учитываются (номера строк в коде меняются от
   сборки к сборке, числа в тексте — от случая к случаю), а пробелы по
   краям строк и подряд идущие пробелы считаются одним пробелом.
6. У группы запоминаются текст и стек последнего отчёта, время первого
   и последнего отчёта.
7. Отчёты хранятся 30 дней. Группа, у которой не осталось отчётов,
   стирается; та же ошибка потом — снова новая.

### Бот
8. Раз в минуту бот ищет новые группы — о которых владельцу ещё не
   писали и чей первый отчёт пришёл не раньше суток назад — и пишет о
   каждой отдельным сообщением владельцу в личку, от старых к новым,
   не больше 5 за проверку (остальные — на следующей):

        Новая ошибка в приложении:
        <текст ошибки, до 500 символов>
        Где: <место>
        Сборка <версия> (<номер>), экран <экран>
        Кто: @<ник> | без входа

   Строки берутся из первого отчёта группы. «Где» — первая строка стека,
   в которой есть `package:moya_dacha/`, иначе первая непустая строка
   стека, без пробелов по краям; нет стека — строки «Где» нет. Нет
   версии — «Сборка ?»; нет экрана — без «, экран …».
9. О группе пишется один раз: после отправки она помечена в базе, и
   перезапуск сервиса повторов не даёт. Группы старше суток без пометки
   (бот не был настроен) не отправляются никогда: старые ошибки
   видны на дашборде.
10. Личка не привязана или бот не настроен — ничего не уходит и ничего
    не помечается.

### Дашборд
11. В `GET /dashboard/data` появляется поле `app_errors` (форма —
    «API»), на странице — раздел «Ошибки приложения» сразу после
    «Ошибок сервера».
12. `app_errors.last_day` — сколько отчётов за последние сутки,
    `app_errors.last_week` — за 7 суток, `app_errors.new_week` — сколько
    групп появилось (первый отчёт) за 7 суток.
13. `app_errors.groups` — до 20 групп с отчётами за 30 дней, по времени
    последнего отчёта, от новых к старым. Поля: `error` (текст последнего
    отчёта), `where` (как в требовании 8, по последнему отчёту; нет —
    пустая строка), `stack` (первые 30 строк стека последнего отчёта),
    `reports` (отчётов за 30 дней), `users` (разных вошедших людей),
    `anonymous` (отчётов без входа), `first_at`, `last_at`, `version`,
    `build`, `screen` и `os` последнего отчёта (нет — пустые строки
    и 0). Нет — `[]`.
14. На странице: плитки «за сутки», «за неделю», «новых за неделю»;
    список групп — время последнего отчёта, сборка, «N отчётов, M людей»,
    текст ошибки, место, стек под «Стек» по касанию. Пусто — «Ошибок
    приложения нет».

### Как это видно из Go (для тестов)
14а. `(*telegram.Bot).CheckAppErrors(ctx) error` — одна проверка из
     требований 8–10; сервис зовёт её раз в минуту рядом с `CheckAlerts`
     (specs/018-telegram-bot.md, требование 21). Сообщение уходит
     методом `sendMessage`, как тревоги.
14б. Стирание старых отчётов (требование 7) идёт вместе со стиранием
     старых измерений машины; тесты его не зовут.

### Приложение
15. Приложение ловит необработанные ошибки Flutter: ошибки при
    построении и отрисовке экрана (`FlutterError.onError`) и ошибки в
    асинхронном коде, которые никто не поймал
    (`PlatformDispatcher.onError`). Ошибки, которые экран поймал и
    показал человеку (нет сети, сервер ответил ошибкой), не
    отправляются.
16. Отчёт уходит молча: человек ничего не видит, не вышло — повтора нет.
    Обычное поведение Flutter при ошибке (вывод в лог, серый экран
    в релизе) не меняется.
17. Одна и та же ошибка (тот же текст) за один запуск приложения
    отправляется один раз, и всего за запуск — не больше 20 отчётов:
    ошибка в каждом кадре не заваливает сервер.
18. С отчётом уходят токен (если человек вошёл), версия и номер сборки
    (specs/017-app-updates.md), последний открытый экран из учёта
    экранов (specs/020-app-sessions.md) и система телефона.

## Вне рамок (Out of scope)
- Падения на уровне Android (Java/Kotlin, «Приложение не отвечает»):
  их ловит только система и Google Play.
- Очередь неотправленных отчётов и повтор после запуска.
- Расшифровка стека обфусцированной сборки: сборка не обфусцируется.
- Отметка «исправлено», закрытие групп, задачи GitHub из ошибок.
- Тревога дашборда по числу ошибок приложения: о новой пишет бот.
- Действия человека перед ошибкой (путь по экранам, касания).

```
POST /api/app-errors                  → 204 | 400 invalid_report | 429 too_many_reports
  {"error": "Null check operator used on a null value",
   "stack": "#0 PostScreen.build (package:moya_dacha/screens/post_screen.dart:120:5)\n...",
   "version": "1.0.0", "build": 386900, "screen": "post", "os": "android 14"}
  Authorization: Bearer … — необязателен
```

Дашборд (дополнение к 016, «API»):

```
"app_errors": {

  "groups": [

     "stack": "…", "reports": 3, "users": 2, "anonymous": 0,
     "first_at": "…", "last_at": "…",
     "version": "1.0.0", "build": 386900, "screen": "post", "os": "android 14"}

```

## Модель данных

```
app_error_groups
  id           uuid        PRIMARY KEY
  fingerprint  text        NOT NULL UNIQUE   -- по требованию 5
  first_at     timestamptz NOT NULL
  last_at      timestamptz NOT NULL
  notified_at  timestamptz                   -- пусто, пока бот не написал

app_errors                                   -- отчёт
  id        uuid        PRIMARY KEY
  group_id  uuid        NOT NULL → app_error_groups, стирается с группой
  at        timestamptz NOT NULL
  user_id   uuid        → users; пусто без входа, человек удалён — пусто
  error     text        NOT NULL
  stack     text        NOT NULL DEFAULT ''
  version   text        NOT NULL DEFAULT ''
  build     bigint      NOT NULL DEFAULT 0
  screen    text        NOT NULL DEFAULT ''
  os        text        NOT NULL DEFAULT ''
```

Время отчёта в тестах сдвигается прямо в базе: `app_errors.at` и
`first_at`/`last_at` группы.

## Ограничения и edge cases
- Ошибка до того, как прочитаны сведения о сборке: версия и номер
  уходят пустыми.
- Человек удалён — его отчёты остаются как отчёты без входа.
- Ошибка в самой отправке отчёта не отправляется: иначе цикл.
- Тексты: «Новая ошибка в приложении:», «Где:», «Сборка», «экран»,
  «Кто:», «без входа», «Ошибки приложения», «Ошибок приложения нет».
