# Спецификация: обратная связь — из приложения и Telegram в задачи GitHub

## Статус
В работе

## Зачем (контекст)
Тестировщики находят баги и придумывают идеи, но сказать о них могут
только владельцу лично, и половина теряется по дороге. Бэклог живёт
в задачах GitHub (ADR-0020), а у тестировщиков нет доступа к репозиторию.
Нужен один путь: человек пишет там, где ему удобно, — кнопкой в приложении,
в теме группы или боту в личку, — а у владельца появляется задача
«входящее». Человек получает номер задачи и потом узнаёт, что идею
одобрили и что она вышла.

Задача: [#43](https://github.com/gmu-msk/moya_dacha/issues/43). Бот —
[018-telegram-bot](018-telegram-bot.md). Почему задачи заводит сам сервис —
[ADR-0023](../docs/adr/0023-feedback-becomes-github-issue.md).

## Пользовательский сценарий

**Дано:** на сервере задан токен GitHub (`FEEDBACK_GITHUB_TOKEN`), бот
работает, группа привязана.

1. Тестировщица открывает «Изменить профиль» → «Написать разработчику», пишет
   «Лента не обновляется после поста», прикладывает скриншот и жмёт
   «Отправить». Ниже на экране появляется её отзыв со статусом
   «Отправлено», через несколько секунд — «Задача #71».
2. В GitHub появилась задача #71 «Отзыв: Лента не обновляется после поста»
   с метками «входящее» и «из приложения»; в теле — текст, скриншот,
   автор, версия приложения и модель телефона.
3. Тестировщик пишет в теме группы «Идеи и баги»: «Хочу сортировать посты
   по культурам». Бот отвечает на его сообщение: «Спасибо! Записал как
   задачу #72. Напишу, когда её одобрят и когда она выйдет в сборке.»
4. Кто-то пишет боту в личку — то же самое, ответ в личке.
5. Владелец пишет боту `/входящие` — список задач «входящее». Пишет
   `/одобрить 72` — бот отвечает «#72 одобрена», а автору идеи приходит
   «Задачу #72 одобрили: её возьмут в работу.»
6. PR с этой задачей слит, деплой отправил сборку в группу. Автору
   приходит «Задача #72 вышла в сборке 386950 — обновите приложение.»
   У тестировщицы из шага 1 в приложении статус меняется на «Вышло в
   сборке 386950».
7. На дашборде видно, сколько отзывов пришло за неделю, и последние десять.

## Функциональные требования

### Отзыв и его путь
1. Отзыв — текст от человека плюс, по желанию, скриншот. Он приходит из
   трёх мест: кнопкой в приложении (`app`), из темы группы и из лички бота
   (оба — `telegram`). Отзыв сначала записывается в базу (таблица
   `feedback`), а задача GitHub заводится потом: GitHub недоступен — отзыв
   не теряется.
2. Статусы отзыва:

   | Статус | Что значит | В приложении |
   |---|---|---|
   | `sent` | записан, задачи ещё нет | «Отправлено» |
   | `accepted` | задача заведена, ждёт решения | «Задача #N» |
   | `approved` | владелец одобрил | «Одобрено, #N» |
   | `declined` | задачу закрыли как ненужную | «Не будем делать, #N» |
   | `done` | задачу закрыли сделанной, сборки ещё нет | «Сделано, #N» |
   | `released` | сделанное вышло в сборке | «Вышло в сборке B» |

### Задача GitHub
3. Сервис заводит задачи сам, в репозитории `FEEDBACK_GITHUB_REPO`
   (по умолчанию `gmu-msk/moya_dacha`) с токеном `FEEDBACK_GITHUB_TOKEN`.
   Без токена отзывы только копятся в базе и видны на дашборде; задачи
   появятся, когда токен зададут.
4. Заголовок — «Отзыв: » и первая непустая строка текста; если она длиннее
   60 символов, берутся первые 60 и «…».
5. Тело:

       <текст отзыва>

       ![скриншот](<полная ссылка на скриншот>)

       ---
       Откуда: приложение | Telegram, тема группы | Telegram, личка
       Автор: <автор>
       Версия: <версия>
       Телефон: <телефон>

   Строки скриншота нет, если его нет. Строк «Версия» и «Телефон» нет,
   если приложение их не прислало (из Telegram их нет никогда).
   Ссылка на скриншот — `PUBLIC_URL` + ссылка хранилища; без `PUBLIC_URL`
   ссылка как есть.
6. Метки: «входящее» и «из приложения» или «из телеграма».
7. Задача заводится сразу после приема, а если не вышло — повторно раз
   в 5 минут, по одной на отзыв: повтор не заводит вторую задачу для
   того же отзыва. Успех переводит отзыв в `accepted` и запоминает номер
   и ссылку задачи.
8. Раз в 5 минут сервис сверяет с GitHub каждую задачу отзывов в статусах
   `accepted`, `approved`, `done`:
   - задача закрыта с причиной `not_planned` или `duplicate` → `declined`;
   - закрыта иначе → `done`;
   - открыта и на ней «одобрено», «в работе» или «на проверке», а отзыв
     в `accepted` → `approved`;
   - иначе статус не меняется.
   GitHub ответил ошибкой на одну задачу — остальные сверяются дальше.

### Ответы автору в Telegram
9. Автор из Telegram получает ответ **на своё сообщение** (в той же теме,
   если оно в теме) после того, как задача заведена:
   «Спасибо! Записал как задачу #N. Напишу, когда её одобрят и когда она
   выйдет в сборке.»
   Если токена GitHub нет, ответ приходит сразу: «Спасибо! Передал
   разработчику.»
10. Переход `accepted` → `approved` — автору: «Задачу #N одобрили: её
    возьмут в работу.» Переход в `declined` и в `done` автору ничего не
    шлёт.
11. Сборка ушла в группу (`build-notify group`, 018 требование 19) —
    сначала сверка из требования 8, потом каждый отзыв в `done` получает
    `released` с номером этой сборки, а автор из Telegram — «Задача #N
    вышла в сборке B — обновите приложение.»
12. Автору из приложения бот не пишет: статус он видит на экране
    «Написать разработчику».
13. Не ушёл ответ автору (бота нет, Telegram ошибся) — статус всё равно
    меняется, повторной отправки нет.

### Приложение
14. На экране «Изменить профиль» над «О приложении» — кнопка «Написать разработчику». Она
    открывает экран с полем текста (до 4000 символов), кнопкой
    «Приложить скриншот» (одна картинка из галереи; выбранную можно
    убрать) и кнопкой «Отправить». Пустой текст не отправляется.
15. Приложение само прикладывает версию «1.0.0 (386900)» из сведений
    о сборке (017) и телефон «<производитель> <модель>, Android <версия>».
16. После отправки поле очищается и показывается «Спасибо! Отзыв
    отправлен.», отзыв появляется первым в списке «Мои отзывы» ниже формы.
17. «Мои отзывы» — свои отзывы, новые сверху, до 50: дата, текст в две
    строки и статус из таблицы требования 2. Пустой список —
    «Здесь появятся ваши отзывы и что с ними стало.»

### Ручки
18. `POST /me/feedback` — multipart: `text` (обязательно, после обрезки
    пробелов 1–4000 символов), `screenshot` (необязательно, JPEG или PNG
    до 10 МБ, сохраняется как фото поста: 1600 по большей стороне, JPEG),
    `app_version` и `device` (необязательно, до 200 символов, длиннее —
    обрезаются). Ответ 201 — отзыв в статусе `sent`. Пустой или слишком
    длинный текст — 400 `invalid_text`; не картинка — 400
    `invalid_image`; больше 10 МБ — 413. Автор — «<имя> (@<ник>)» или
    «@<ник>», если имени нет.
19. `GET /me/feedback` — свои отзывы, новые сверху, не больше 50.
    Чужих не видно.

### Telegram
20. `/ideas` или `/идеи` от владельца в группе привязывает **тему для
    идей**: роль `ideas`, номер чата и номер темы (`message_thread_id`,
    если сообщение в теме). Ответ: «Готово: сообщения отсюда станут
    задачами.» Привязка без темы — отзывом становится любое сообщение этой
    группы.
21. Отзывом становится сообщение не от бота и не команда:
    - в личке боту — от кого угодно, владельца тоже;
    - в привязанной группе — только в привязанной теме (если тема
      задана); остальные сообщения группы бот молча пропускает.
    Текст — `text` или подпись к фото (`caption`); у фото берётся самый
    большой размер (`getFile`, затем файл по
    `<APIURL>/file/bot<Token>/<file_path>`). Фото без подписи — текст
    «Скриншот без подписи». Не скачалось фото — отзыв без скриншота.
    Сообщение без текста и без фото (стикер, голосовое) бот пропускает.
22. Автор из Telegram — «@<ник>», а без ника — имя и фамилия.
23. Любая команда в личке не от владельца получает ответ «Здравствуйте!
    Это бот МоейДачи. Напишите сюда идею или что сломалось — я передам
    разработчику и пришлю номер задачи.» (заменяет текст 018,
    требование 7).
24. `/inbox` или `/входящие` от владельца — открытые задачи с меткой
    «входящее», новые сверху, до 20 (PR не считаются):

        Входящие:
        #72 Отзыв: Хочу сортировать посты по культурам
        #71 …

    Нет таких — «Входящих нет.»
25. `/approve N` или `/одобрить N` от владельца — метка «одобрено» на
    задаче N (снять «входящее» — дело прогона «Бэклог»). Ответ «#N
    одобрена.» Если у задачи есть отзыв в `accepted`, он сразу становится
    `approved` с ответом автору из требования 10. Нет числа — «Напишите
    номер задачи: /одобрить 71». GitHub ответил 404 — «Задачи #N нет.»
26. Без токена GitHub `/inbox` и `/approve` отвечают «GitHub не настроен:
    нет FEEDBACK_GITHUB_TOKEN.»

### Дашборд
27. На дашборде блок «Отзывы»: сколько пришло за 7 дней и последние 10 —
    время, откуда, автор, текст (обрезан до 140 символов), статус, номер
    задачи ссылкой. В `/dashboard/data` это поле `feedback`:
    `{"week": N, "recent": [{"created_at", "source", "author", "text",
    "status", "issue", "issue_url"}]}`; `issue` и `issue_url` — null,
    пока задачи нет.

### Настройка
28. Деплой переносит секрет `FEEDBACK_GITHUB_TOKEN` в `/etc/moya-dacha.env`
    так же, как токен бота; `PUBLIC_URL` — `https://<домен>`. Токен —
    fine-grained, только на этот репозиторий, права Issues: read and write.
29. `telegram-check` в итоге деплоя пишет строку про GitHub: «GitHub:
    задачи в <репозиторий>», «GitHub: FEEDBACK_GITHUB_TOKEN не задан —
    отзывы копятся в базе» или «GitHub: не принял токен: <ошибка>».

### Как это видно из Go (для тестов)
30. `feedback.New(db *pgxpool.Pool, cfg feedback.Config) *feedback.Service`,
    `Config` — `Token`, `Repo` (по умолчанию `gmu-msk/moya_dacha`),
    `APIURL` (по умолчанию `https://api.github.com`), `PublicURL`, `Media`
    (`media.Storage` для скриншотов из Telegram).
31. `feedback.Notifier` — `Notify(ctx, to feedback.Recipient, text string)
    error`, `Recipient` — `ChatID`, `ThreadID`, `ReplyTo` (номер сообщения
    автора). `*telegram.Bot` — Notifier: пишет `sendMessage` с
    `message_thread_id` (если не 0) и `reply_parameters.message_id`.
32. `(*Service).Sync(ctx, n Notifier) error` — один проход: завести
    задачи для `sent` (требование 7, с ответом из требования 9) и сверить
    статусы (8, с ответом из 10). `(*Service).Release(ctx, build int64,
    n Notifier) error` — требование 11. `n` может быть nil — тогда
    ответов нет.
33. `api.Config.Feedback *feedback.Service` — через него ручки записывают
    отзыв и сразу в фоне заводят задачу. nil — сервис делает свой, без
    GitHub, с хранилищем `api.Config.Media`.
34. `telegram.Config.Feedback *feedback.Service` — через него бот
    записывает отзывы и отвечает на `/inbox`, `/approve`. nil — отзывы из
    Telegram не принимаются, `/inbox` и `/approve` отвечают как в
    требовании 26.
35. С GitHub сервис говорит REST API по адресу `APIURL` с заголовками
    `Authorization: Bearer <токен>` и `Accept: application/vnd.github+json`:
    - `POST /repos/{repo}/issues` `{title, body, labels}` → 201 `{number,
      html_url}`;
    - `GET /repos/{repo}/issues/{n}` → `{number, state, state_reason,
      labels: [{name}]}`;
    - `GET /repos/{repo}/issues?labels=входящее&state=open&per_page=20`
      → `[{number, title, pull_request?}]`;
    - `POST /repos/{repo}/issues/{n}/labels` `{"labels": ["одобрено"]}`.
    Ответ не 2xx — ошибка.

## Вне рамок (Out of scope)
- Пуш-уведомление автору из приложения: статус виден на экране отзывов.
- Ответ владельца автору из GitHub-комментария в Telegram.
- Метка «идея» или «баг»: вид отзыва выбирает владелец при разборе.
- Несколько скриншотов в одном отзыве, видео, файлы-документы из Telegram.
- Ограничение частоты: тест закрытый, двадцать человек.

## API / контракт данных
`specs/openapi.yaml`: `GET` и `POST /me/feedback`, схема `Feedback`
(`id`, `text`, `status`, `created_at`; `issue` — только когда задача
заведена, `build` — только у `released`).

## Модель данных

```
feedback
  id            bigserial   PRIMARY KEY
  source        text        NOT NULL  'app' | 'telegram'
  user_id       uuid        NULL → users ON DELETE SET NULL
  author        text        NOT NULL
  tg_chat_id    bigint      NULL      куда отвечать
  tg_thread_id  bigint      NULL
  tg_message_id bigint      NULL
  tg_private    boolean     NOT NULL DEFAULT false
  text          text        NOT NULL
  screenshot    text        NULL      ключ хранилища
  app_version   text        NULL
  device        text        NULL
  status        text        NOT NULL DEFAULT 'sent'
  issue         int         NULL
  issue_url     text        NULL
  build         bigint      NULL      сборка, в которой вышло
  created_at    timestamptz NOT NULL DEFAULT now()

telegram_chats
  + thread_id   bigint      NULL      тема для роли ideas
  role          + 'ideas'
```

## Ограничения и edge cases
- Отзыв удалённого аккаунта остаётся без автора в `user_id`, строка
  «Автор» в задаче остаётся.
- Скриншот лежит в хранилище по случайной ссылке и открывается без входа:
  иначе GitHub его не покажет. Ссылку знают только те, кто видит задачу.
- Токен GitHub в логах не пишется.
- Сообщение в группе, отредактированное после отправки, отзывом второй
  раз не становится: бот читает только новые сообщения.

Тексты:
- «Спасибо! Записал как задачу #N. Напишу, когда её одобрят и когда она
  выйдет в сборке.», «Спасибо! Передал разработчику.»
- «Задачу #N одобрили: её возьмут в работу.»
- «Задача #N вышла в сборке B — обновите приложение.»
- «Готово: сообщения отсюда станут задачами.»
- «Входящие:», «Входящих нет.», «#N одобрена.», «Задачи #N нет.»,
  «Напишите номер задачи: /одобрить 71»,
  «GitHub не настроен: нет FEEDBACK_GITHUB_TOKEN.»
- Приложение: «Написать разработчику», «Приложить скриншот»,
  «Отправить», «Спасибо! Отзыв отправлен.», «Мои отзывы», «Здесь
  появятся ваши отзывы и что с ними стало.»

## Критерии готовности (Definition of Done)

- [ ] Отзыв из приложения становится задачей со скриншотом, версией
      и телефоном
- [ ] Сообщение в теме «Идеи и баги» и в личке становится задачей, автор
      получает номер
- [ ] `/входящие` и `/одобрить N` работают, автор узнаёт об одобрении
- [ ] После сборки в группу автор узнаёт, что вышло
- [ ] Отзывы видны на дашборде
- [ ] Есть сценарий показа `demo/stories/019-feedback/`
      ([ADR-0009](../docs/adr/0009-demo-story-per-feature.md))
