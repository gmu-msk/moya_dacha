# 0023. Отзыв становится задачей GitHub, заводит её сам сервис

Бэклог — задачи GitHub (ADR-0020), а у тестировщиков нет доступа к
репозиторию. Отзывы приходят из приложения, из темы группы и из лички бота
(specs/019-feedback.md), и все они должны стать задачами «входящее».

## Решение

* Отзыв сначала ложится в таблицу `feedback`, потом сервис заводит задачу
  через REST API GitHub токеном `FEEDBACK_GITHUB_TOKEN`. GitHub недоступен
  или токена нет — отзыв ждёт в базе, сверка раз в 5 минут повторяет.
* Токен — fine-grained, только на этот репозиторий и только Issues. Он
  лежит в `/etc/moya-dacha.env`, как токен бота; деплой переносит его из
  секрета репозитория.
* Статус отзыва сервис узнаёт, сверяя задачу раз в 5 минут: метка
  «одобрено» — одобрено, закрыта — сделано. «Вышло» — когда сборка main
  ушла в группу: это единственный момент, когда сделанное правда есть
  у людей в руках.
* Скриншот лежит в хранилище сервиса (ADR-0011) по случайной ссылке без
  входа, в задаче — картинка по полной ссылке `PUBLIC_URL`.

## Почему не так

* **GitHub Actions по `repository_dispatch`.** Задачу завёл бы прогон
  с его собственным токеном, но сервису всё равно нужен токен — чтобы
  позвать прогон, — а статусы пришлось бы возвращать обратно вебхуком.
* **Вебхук GitHub на сервис вместо сверки.** Быстрее на минуты, но нужен
  секрет вебхука, открытая ручка и разбор подписей; для двадцати человек
  сверка раз в 5 минут дешевле.
* **Загрузка скриншота в сам GitHub.** У REST API нет загрузки картинок
  в задачи; класть их в репозиторий коммитами — мусор в истории.

## Следствия

* Без токена фича наполовину работает: отзывы видны на дашборде, авторы
  из Telegram получают «Спасибо! Передал разработчику.»
* Скриншоты доступны всем, у кого есть ссылка. Ссылку видят только те,
  кто видит задачу.
