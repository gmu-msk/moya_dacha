# 0008. Dart-клиент генерируется openapi-generator-ом и лежит отдельным пакетом

ADR-0001 требует, чтобы клиент для приложения генерировался из
`specs/openapi.yaml`, но не называет инструмент. Инструмент —
[openapi-generator](https://openapi-generator.tech) в режиме `dart`,
версия зафиксирована в `Makefile`. Результат — полноценный Dart-пакет
в `mobile/packages/moya_dacha_api`, подключённый к приложению
path-зависимостью и закоммиченный в git.

## Почему именно так

- **Режим `dart`, а не `dart-dio`.** Он даёт код на обычном `http` без
  `build_runner`: один шаг генерации вместо двух, и на машине разработчика
  не появляется второй генератор со своим кэшем.
- **Отдельный пакет, а не папка внутри `lib/`.** Генератор выдаёт пакет
  со своим `pubspec.yaml` и внутренними импортами вида
  `package:moya_dacha_api/...`; вложить его в `lib/` приложения нельзя,
  не правя импорты руками — а руками сгенерированное не правится.
- **Jar генератора в git не хранится.** 31 МБ, скачивается в `.cache/`
  при первом `make generate` по закреплённой версии. Герметичность сборки
  от этого не страдает: в git лежит сгенерированный код, а генератор нужен
  только чтобы перегенерировать и чтобы CI поймал дрейф — ровно как
  `go tool oapi-codegen` на серверной стороне.
- **Версия генератора закреплена явно.** Смена версии переписывает весь
  сгенерированный код, поэтому обновление генератора — отдельный осознанный
  коммит, а не побочный эффект чужой машины.

## Следствия

- Для `make generate` нужна Java 17+; в CI она ставится отдельным шагом.
- Анализатор не смотрит на `mobile/packages/moya_dacha_api` — предъявлять
  замечания к сгенерированному коду некому.
- Когда появится iOS, клиент у него тот же самый: пакет не зависит
  от платформы.
