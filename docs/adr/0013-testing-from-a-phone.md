# 0013. Проверка фичи с телефона: сборка в релизе PR, адрес сервера — в приложении, стенд по команде

Владелец проекта ставит задачи и проверяет результат с телефона, без
компьютера. Поэтому путь «увидел фичу своими глазами» не должен требовать
ничего, кроме телефона: ни `make`, ни USB-кабеля, ни машины в той же сети.

Решение состоит из трёх частей.

## 1. Тестовая сборка — черновым релизом PR

На каждый пуш в PR CI выкладывает собранный APK релизом `pr-<номер>`
(черновик, `prerelease`) и пишет в PR один комментарий с прямой ссылкой,
переписывая его на каждой следующей сборке. Ссылка открывается в браузере
телефона и ставится как обычный APK.

Артефакт прогона для этого не годится: он отдаётся zip-архивом, который на
телефоне надо ещё распаковать. Google Play (внутреннее тестирование) и
Firebase App Distribution — правильный путь, когда тестировщиков станет
двадцать; пока тестировщик один, они стоят заведения аккаунтов, ключа
подписи и сервисного ключа в секретах, а дают то же самое.

Репозиторий приватный, поэтому ссылка на APK работает у того, кто вошёл в
GitHub в браузере телефона.

Когда PR закрыт или влит, релиз с тестовой сборкой удаляется: список
релизов — список настоящих версий, а не свалка сборок.

## 2. Адрес сервера задаётся в приложении, а не при сборке

Раньше адрес зашивался в APK при сборке (`--dart-define=API_BASE_URL`), и
под каждый стенд собирался свой APK. С телефона это тупик: собрать APK
телефоном нечем.

Теперь адрес — значение, которое человек вводит на экране «Сервер»
(нажатием на адрес внизу любого экрана, в том числе до входа). Зашитый при
сборке адрес остался значением по умолчанию: эмулятор, `make story` и
прогон на CI работают как работали.

Следствия:

- одна сборка из PR годится для любого стенда: временного, на машине
  в локальной сети и, когда он появится, настоящего;
- при смене адреса сессия стирается: токен живёт на том сервере, где его
  выдали (ADR-0010);
- адрес проверяется кнопкой «Проверить» до сохранения — иначе ошибка в
  адресе выглядит как немой экран входа.

## 3. Пока нет сервера — временный стенд по команде в PR

Настоящего сервера нет и не будет, пока не закрыт вопрос 152-ФЗ и места
хранения персональных данных (specs/000-overview.md, ADR-0005: сред две,
локальная и прод). Но тестовой сборке нужно куда-то ходить.

Команда `/стенд` в PR поднимает на раннере GitHub Actions тот же стенд, что
`make demo` поднимает локально, из кода этого PR, и выдаёт ему публичный
адрес быстрым туннелем Cloudflare. Адрес приходит ответным комментарием,
стенд живёт заданное число минут (по умолчанию 30, максимум 60) и гаснет
сам; `/стенд стоп` гасит раньше.

Почему так, а не иначе:

- **аккаунтов и денег не нужно**: быстрый туннель не требует регистрации,
  раннер уже есть;
- **персональные данные нигде не оседают**: стенд живёт десятки минут,
  данные на нём выдуманные, вместе с раннером исчезает и база. Вопрос
  152-ФЗ этим не решается и не обходится — он просто не возникает;
- **это не staging**: стенд не переживает прогон, не имеет своих секретов
  и своей истории миграций, поэтому ADR-0005 остаётся в силе.

Цена — минуты GitHub Actions: стенд тратит их ровно столько, сколько живёт.
Отсюда потолок в час и команда «стоп».

Когда сервер появится, третья часть решения меняется на один постоянный
адрес, а первые две остаются как есть.

## Цикл работы, который из этого складывается

1. Задача ставится в треде проекта или комментарием в PR.
2. CI собирает APK и присылает ссылку комментарием.
3. `/стенд` — приходит адрес.
4. Установка по ссылке, адрес вставляется в приложении, фича проверяется
   глазами по сценарию показа (ADR-0009).
5. Замечания — комментарием в PR или в треде; правки приезжают новой
   сборкой в тот же комментарий.
6. Всё устраивает — PR мерджится с телефона.
